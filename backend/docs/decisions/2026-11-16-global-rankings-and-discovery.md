## 来源分工

| 来源 | 热播信号 | 新片/新集更新信号 | 使用边界 |
| --- | --- | --- | --- |
| 豆瓣 | 中文电影、剧集等明确榜单的榜位与升降 | 有明确上映或节目更新事件时间的条目 | 高评分榜不等于热播；挑战页、取数失败不作为空榜成功 |
| TMDB | movie/tv 的 day、week 趋势，保留榜位和媒体类型 | 上映/发行日期、今日播出、剧集与季集的实际播出日期 | first_air_date 不是最近一集日期；now_playing 表示影院上映，不表示本站可播 |
| IMDb | 可取得的 Most Popular/MOVIEmeter 等趋势；投票量辅助判断可信度 | 可核实的发行/季集播出事件 | Top 250、averageRating 不作为实时热度；免费数据集并不提供完整榜位，官方 API 有独立接入要求 |
| Rotten Tomatoes | 明确的 Most popular 顺序 | 明确的 Newest/Latest Episode 对应事件与日期 | Tomatometer/Popcornmeter 是口碑信号；不把采样日期当作品更新时间，API/data feed 以实际可用接口为准 |

不同来源保留独立信号，不能直接把豆瓣 8.5、IMDb 8.5、烂番茄 90% 相加。按榜位、近期升降、多源共同出现与时间衰减融合，口碑与投票量只作为有边界的辅助。先按电影、剧集、动漫、综艺等类别分别生成榜，再做首页多样性选择。无法获得权威榜单的类别沿用对应类别策略，不能伪造外部趋势。

## 自动流程

1. **采样并保存来源快照**：记录 provider、board、media_type、external_id、rank、来源窗口、collected_at、来源实际事件日期、评分和投票量。保留最后成功快照；缺失字段为 NULL，来源失败明确标记，不伪装成榜单已刷新。
2. **识别聚合作品**：优先采用已验证的外部 ID；TMDB movie 与 tv 的数字 ID 处于不同命名空间，剧集还须处理季与集的身份。标题、年份、别名只用于受控辅助，冲突进入待确认，不用 0 占位或低阈值强行合并。
3. **先建目录条目**：未收录作品创建稳定聚合 ID，保存已知标题、来源身份、分类和日期，未知元数据留空。创建聚合条目不等于完成资源采集、增强或人工审核。
4. **进入全网榜单**：可展示条目与来源理由；没有本站资源时显示“资源收集中”，不显示成可立即播放。分别展示“全网已播到第 12 集”和“本站可看至第 10 集”等状态。
5. **生成持久补抓请求**：新条目、已有条目缺资源、已有剧集落后于外部新集都可触发。使用作品、季集和目标资源版本去重，按热度、时效与缺口排序，受队列背压、源站配额和并发上限约束。补抓提交失败可自动恢复；周期刷新榜单不重复创建任务或代理实例。
6. **沿用四阶段流程补齐**：采集 → 清洗 → 增强 → 聚合，随后校验资源可用性并更新条目状态。搜索条件中的预期 ID 不能当作源站真实返回 ID；补抓结果仍需独立身份校验，不能为填满榜单而强绑。

缺少评分、演员、海报等元数据时也允许先建条目再补齐；缺失评分不能回填为 10 分。真实评分 0 与缺失值要区分。

## 榜单与时间契约

- **全网热播**：反映外部近期关注程度，不能用单次同步完成时间或评分冒充热度。
- **全网最近更新**：电影发行/上线、剧集新季新集播出等真实事件，保存事件类型、日期精度、地区及季集；首次上映、首播日期与最新集日期分开。
- **本站资源更新**：本站新增可播放资源的事件，单独维护；资源补抓完成与全网节目更新不能共用一个时间字段。
- collected_at、source_event_at/date、metadata_updated_at、resource_updated_at 独立维护。源只给日期时不伪造精确更新时间；补抓、海报修复、聚合重算不把旧作品刷新成“刚更新”。
- 初始建议趋势采样 30—60 分钟、榜单物化 5—15 分钟，缓存按现有 L1/L2/L3 体系复用；实际频率配置化，并公开最后成功采样时间。上游不可用时降级至仍有效的快照，超期后明确提示，不能长期保留伪实时榜单。

## 实施范围与验收

### 出站与代理约束（用户补充）

系统发起的公网 HTTP 请求默认优先经已有 Oracle/CF 代理池，复用已有 sing-box 网关和 HTTP transport；内部服务、集群控制面及明确的内网数据源保持内网路由。榜单、权威详情、资源补抓、磁链、图片、AI/LLM、OAuth 和公网 webhook 统一检查实际装配，不能仅因使用同名客户端便假定已走代理。图片仍执行严格目的地址和重定向检查。显式关闭代理可以直连；已开启时端点不可用、配置暂失或全池冷却应报出可恢复失败，不静默直连。不得逐请求创建代理进程，不记录 API key 或代理订阅令牌。

### 实施契约

在既有 trend HTTP 契约中向后兼容增加来源榜单与逐条信号：来源、榜名、媒体类型、来源 ID、榜位、时间窗口、采样时间、真实事件日期、季集和来源 URL。旧字段及旧调用保持可用，但没有来源榜位的旧批次不冒充全网热度。来源状态与最后成功快照分开保存；补抓由持久状态驱动并以作品/季集和冷却窗口去重。新增结构使用独立 Liquibase 迁移，不改历史迁移。

预期涉及 scraper 的来源采样与真实调度、content 的快照与聚合条目写入、task 的补抓去重与恢复、portal 的榜单查询、huawai 的来源/更新时间/资源状态展示及必要数据库迁移。优先复用现有模块、鉴权、缓存、限流和队列，不创建平行项目或手工代替系统改榜。

验收须覆盖：多源快照不互相覆盖；旧高分片不会因后台改字段冒充最新；跨媒体同号和跨季不误绑；先建条目后资源可用；已有缺资源作品也会补抓；重复采样不重复建条目或任务；失败源不误报成功；权限、成人隔离和人工锁定不退化。用真实外部小样本与生产只读结果核验新鲜度、过期比例、资源缺口和补抓延迟，不以拒绝率或已部署代替推荐效果。

实现后只通过 GitHub Actions 测试与 Native 构建，按实际受影响模块发布；本地不编译，不人工批量改库、清队列或购买外部数据订阅。

## 3.7.0 实施与交付边界（2026-11-17）

- 数据结构：新增 typed catalog identities、独立来源板状态/最后成功快照、榜位观察、不会随日榜轮换删除的节目事件、持久资源补抓与独立元数据补齐队列。原始视频、绑定、用户数据、访问控制和人工锁不迁走、不清空。
- 采样：scraper 开启真实定时调度，旧默认凌晨三点升级为每半小时，自定义 cron 保留；多实例共用带续租的分布式锁。TMDB 保存日/周榜、实际上映和验证过的新集事件；Douban/RT 独立失败不清空最后成功榜。IMDb 无官方授权接口时明确 UNAVAILABLE。
- 融合：只对明确来源窗口计分，同一来源日/周贡献取最大值，周榜权重 0.65，使用榜位、有限升降/多源加权和时间衰减；七天过期，不使用评分或后台 updated_at 冒充热度。最近更新查询真实上映/新集事件，与趋势采样新鲜度独立。
- 补抓：新条目及已有缺资源/落后新集条目持久排队，默认每轮 5 个目标、每目标至多 3 个符合既有配置的源，全局活跃采集任务门限 24；原子领取、租约 fencing、退避、失败恢复和人工暂停保护。搜索目标身份只是上下文，不写成源站返回的身份事实。
- 独立补齐：无 raw 资源的目录也可通过 metadata-worker 获取 TMDB 权威详情；实际返回 ID、电影/剧集结构及季号须验证。只填缺字段，保留人工锁/已有值/成人及可见范围；缺字段仍 DIRTY，未取得可信来源则日级 UNAVAILABLE 重试。Douban/RT 暂无同等强度的详情证据时不强行增强，已有明确 TMDB 身份可复用。索引交接独立持久重试。
- 聚合保护：无 raw 的目录不进入 raw 重算，也不因空重算被标 SYNCED；已验证目录元数据在后续 raw 重建时保留，资源动态信息仍走原流程。
- 资源口径：三服务共用资源清单函数，只认合法 HTTP(S) 或有来源域的相对路径，排除成人受限与跨季 raw；明确集号取最大值，不以镜像或播放列表数量充当更新集数。“已收录”不等于完成远端播放探活，也不承诺连续集数。
- 前台：保留已有版式，新增全网最近更新、来源与实际北京时间采样状态，以及全网播出/本站收录的区分；无资源不再显示立即播放，融合分不作为全网计数。首页按真实请求渲染、数据缓存保留；后端异常不被缓存成新鲜空榜。封面原生 img 属浏览器请求，服务端图片下载走既有严格代理通道。
- 出站：复用 Oracle/CF/sing-box 网关；为图片、Google Decisions、LLM、磁链、OAuth、样例抓取及公网 webhook 补齐实际装配。内部服务和明确内网图片直连；AI POST 不自动重试以防重复计费。生产只读核验 pool 配置与 ConfigMap 均启用两池，不新增代理进程。

本地仅执行版本契约、CI 工具回归、workflow 静态检查及前台轻量测试。Java、PostgreSQL/Valkey 集成测试、前台构建和两架构 Native 均由 GitHub Actions 执行；待 CI/运行态证据后更新本节。

### 3.7.6 生产验证反馈

3.7.5 已晋级 `124b25f`，生产完整迁移成功。首轮自动采样取得豆瓣电影和剧集榜单，资源补抓已自主提交任务。采集日志同时暴露 Native 无法绑定凭据服务的 `ProviderCredentialLease`；内容服务录得同一轮两次 POST，单次执行约 178–207 秒，而 scraper 实际配置为 30 秒且会立即重试。

本次修复明确为 scraper 和 content 两个模块。为 scraper 补齐凭据回包绑定和离线启动探针。采样按独立榜单顺序提交，只发送一次，不重复传输榜单中的作品列表，按实测将单榜默认时限设为 120 秒，保留运维覆盖。某榜提交失败时保留该榜最后成功状态并继续处理其他榜单。同一作品在多个榜单出现仍使用目录身份去重。content 将快照和实际事件改用 JDBC 批量写入，统一比较 PostgreSQL 的微秒时间精度。生产发现 Rotten Tomatoes 已创建目录身份但快照缺失，原因是数据库将纳秒值进位后，首份样本被误判比刚写入的状态更旧。回归覆盖该首写和重放。API、已部署迁移及存量数据契约保持兼容。GitHub Actions 验证凭据绑定、失败隔离和两架构 Native，生产等待调度自动采样核对接口和最新事件。

3.7.6 (`8f8e223`, Actions `44225134462`) 的 226 项 Java 回归和三个 Native 架构作业通过。scraper ARM64 在 8 GiB 构建堆生成镜像时耗尽内存，门禁阻止晋级。3.7.7 仅将该模块 ARM64 作业改用 10 GiB、2 路并行的构建配置，其他模块保持既有预算。标准 runner 实测 15.57 GiB，此调整只发生在 GitHub Actions，不改变 Kubernetes 的资源配额。3.7.6 镜像和版本保留，不覆盖或部署。

### 3.7.8 播放列表消费与补抓验收

生产抽查发现，新目录已绑定的 11 条原始记录都带匹配 ID 的 `vod_play_from`、`vod_play_url`，映射已配置，实际节目链接尚未写入。RabbitMQ 约 760 条待处理、1833 条历史死信。过去 30 分钟播放同步 46 次失败，约 30.2 秒，消费者日志为 `TransactionTimedOutException`。播放事务对每集分别写域名和节目，在跨节点数据库连接上放大延迟。

保留旧版播放列表替换契约，在同一个短事务里锁定原始视频版本，批量写播放列表和节目，同一次同步中的域名按固定顺序只写一次。每批最多 256 行，保持现有 URL 与域名规范。补抓再次收到同版本但尚未存下任何节目的数据时，只重新提交播放入库任务，避免归一化和聚合重复执行。Native 运行验证使用 513 集和真实 PostgreSQL/RabbitMQ，验证节目全部提交、同域复用及旧消息无法覆盖新版本。线上通过新消费速度、连接等待、失败数及目录资源记录验证，历史死信保留。

构建计划同时修复一处快速预检。新候选即使仅变了 CI 与 `VERSION`，也要读取上次晋级账本，才能发现上一失败候选遗留的应用改动。版本号自身不强制重建任何应用。

公网页面验收发现逐榜状态常驻时挤占热播列表。前台保留现有卡片和榜单，只将来源状态改为可展开明细，折叠时显示本轮有有效样本的来源。近期更新卡片保留一次资源缺口提示。

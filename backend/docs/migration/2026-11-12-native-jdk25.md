## 采集和队列行为

- `RawVideoIngestionTransactions` 仅在持久化及播放列表替换时持有短事务；Rabbit/Valkey 发布在事务返回后执行。PENDING 记录重投修复提交成功但交接失败，READY 同版本跳过。
- `RabbitConfirmedPublisher` 等待 correlated broker confirm，拒绝 nack、不可路由和确认超时；消费重试/死信发布成功后才 ACK 原消息。基础设施失败保留原消息并 requeue。确认默认 `ircs.messaging.publish-confirm-timeout=PT10S`。
- 采集 page/detail 使用虚拟线程，默认 `app.scraper.task-queue.processing-timeout=PT5M`；超时取消任务，并在外部调用及发布后续任务前检查期限，防止迟到任务继续扩散工作。
- Rabbit consumer、任务执行器实际使用虚拟线程。并发、prefetch、队列容量继续构成背压；关闭过程不会让满队列提交者无限等待。
- Runtime queue 在 Lua 中返回领取时的原子快照；完成/失败按 submissionId、ownerId、attempt 隔离，旧消费者无法结束新尝试。领取前主动回收超时，不依赖 ops 服务存活。
- `app.runtime-work-queue.max-attempts=5` 限制单轮失败和可见性超时次数，耗尽进入 DLQ。人工重放获得新一轮有限额度，attempt 继续递增，保留旧尝试隔离；原重放次数上限仍有效。
- 元数据和归一化按并行容量分波领取，减少已领取却在本地排队过期。归一化默认并行 2，并受 Hikari `maximum-pool-size - 1` 预算约束，至少保留一个连接供调度/状态使用。
- 图片/R2/头像网络与文件操作移出数据库事务。R2 更新增加状态及路径条件，保留 PENDING_DELETE，失败不覆盖删除或已完成状态，防止耗时 I/O 返回后恢复过期状态。

交付仍是至少一次处理：网络超时可能发生于 broker 已接收但客户端未收到 confirm 的窗口，后续消费者必须保持幂等。没有事故现场数据，不能把上述修复写成生产事故根因已经全部证实。

## Native 与 Actions

`.github/workflows/native-build.yml` 自动触发于 `main`、`upgrade/**`，也支持手动选择 Java build_scope。Java 回归使用真实 Valkey；Python 测试生成本地微型 BERT，执行真实 CPU 推理和 HTTP 校验，无需下载测试模型。

矩阵从 settings.gradle 推导 22 个 Java 部署模块，在对应 amd64/arm64 runner 使用 `scripts/docker/Dockerfile.native`，含共享 DTO、缓存/队列类型、JJWT、SQL/Lua、字典等运行时 hints。运行镜像保留 Native 编译目录中的本地库。CI 在临时 Valkey 上验证内容安全 HTTP/JSON/字典，在临时 PostgreSQL 上执行 Native migrator 并核对 Liquibase 记录。

自动构建使用本仓库 `GITHUB_TOKEN` 发布 GHCR 的提交 SHA tag；仅全部检查通过后生成双架构 manifest。无自动生产 tag、GitOps 变更或部署。原 Docker Hub 手动工作流支持 native/jvm，两种模式的 tag 分离。两套前端在各自已有仓库运行 Node 26 `npm ci`、lint、build，并保存可下载产物。

## 发布与回滚

尚未切换生产。候选镜像通过 Actions 后，部署时引用固定 `sha-<完整提交SHA>` 或 digest，先灰度采集链路；核对 backlog、unacked、重试/DLQ、处理耗时、Hikari active/pending/timeout 及业务入库结果，再逐步扩展。

运行时回退可恢复部署前的 JVM 镜像 digest；需要包含本次可靠性修复的 JVM 候选时，在原 Docker Hub 手动工作流选择 `image_mode=jvm`。本次未新增数据库迁移或改变队列 key/version，新增 Redis 字段可由旧代码忽略。滚动更新期间避免新旧消费者共用同一任务类型并长时间并行，因为旧版本不具备新增 fencing。

源码回退点为三个仓库的上述基线提交；保留 GitHub 分支和构建日志供核验，不自动 reset/force-push 或删除生产队列。

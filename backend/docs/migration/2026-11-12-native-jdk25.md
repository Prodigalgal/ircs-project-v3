# V3 Native、JDK 25 与采集消费可靠性升级

## 范围与起点

V3、V4 均按生产系统对待。本次保留 V3 的 21 个独立 Java 服务、独立 migrator 和 Python 服务，Java 主版本保持 25。沿用 `Prodigalgal/ircs-project-v3`，将后端、管理端和门户整合成一个仓库；原后端起点 `f02abeb15b5b`，管理端起点 `5c08781`，门户起点 `f0dc336`。

用户授权全栈依赖升级、Native、虚拟线程、采集可靠性修复、GitHub Actions 构建、生产 V4 下架及 V3 接入原私有 GitOps。生产数据库、消息、缓存和持久卷继续使用，不清库、不清队列、不删除数据卷；不制作 Git 或数据备份。四个旧拆分仓库 ircs-huawai-frontend、ircs-admin-frontend、ircs-backend、ircs-frontend 已按授权删除并验证 404；V3 源码与私有 GitOps 仓库保留。

缺少历史事故日志。代码回归覆盖明确的故障路径；本次现场另外证实了 Valkey 满卷及 AOF 非法填充，已恢复真实读写。生产吞吐、积压及连接池还需以切换后的观测为准。

## 采集和队列行为

- `RawVideoIngestionTransactions` 仅在持久化及播放列表替换时持有短事务；消息和运行队列发布在事务返回后执行。PENDING 记录重投修复提交成功但交接失败，READY 同版本跳过。
- `MessagePublisher` 接口的 `ConfirmedMessagePublisher` 适配器等待 correlated broker confirm，拒绝 nack、不可路由和确认超时；消费重试/死信发布成功后才 ACK 原消息。基础设施失败保留原消息并 requeue。确认默认 `ircs.messaging.publish-confirm-timeout=PT10S`。
- 运维人工重放死信同样使用手动确认：`basicGet(autoAck=false)` 读取，持久化重发收到 broker confirm 后再 ACK；失败 NACK/requeue 原消息。重放保留 payload、记录次数并重置本轮有限重试额度；原有 HTTP 接口保持兼容。新增成功顺序、失败保留和显式丢弃三个回归用例。
- 采集 page/detail 使用虚拟线程，默认 `app.scraper.task-queue.processing-timeout=PT5M`；超时取消任务，并在外部调用及发布后续任务前检查期限，防止迟到任务继续扩散工作。
- Rabbit consumer、任务执行器实际使用虚拟线程。并发、prefetch、队列容量继续构成背压；关闭过程不会让满队列提交者无限等待。
- Runtime queue 在 Lua 中返回领取时的原子快照；完成/失败按 submissionId、ownerId、attempt 隔离，旧消费者无法结束新尝试。领取前主动回收超时，不依赖 ops 服务存活。
- `app.runtime-work-queue.max-attempts=5` 限制单轮失败和可见性超时次数，耗尽进入 DLQ。人工重放获得新一轮有限额度，attempt 继续递增，保留旧尝试隔离；原重放次数上限仍有效。
- 元数据和归一化按并行容量分波领取，减少已领取却在本地排队过期。归一化默认并行 2，并受 Hikari `maximum-pool-size - 1` 预算约束，至少保留一个连接供调度/状态使用。
- 图片/R2/头像网络与文件操作移出数据库事务。R2 更新增加状态及路径条件，保留 PENDING_DELETE，失败不覆盖删除或已完成状态，防止耗时 I/O 返回后恢复过期状态。

交付仍是至少一次处理：网络超时可能发生于 broker 已接收但客户端未收到 confirm 的窗口，后续消费者必须保持幂等。没有事故现场数据，不能把上述修复写成生产事故根因已经全部证实。

## 中间件边界与命名

52 个自有 Java 文件按缓存、消息、工作队列、租约和死信等能力重新命名，移除 Redis/Valkey/Rabbit 品牌前缀。代表性名称：`DistributedRuntimeWorkQueue`、`ClusterLockManager`、`DistributedLeaseService`、`SystemConfigCache`、`MetadataNameCache`、`DistributedTaskProgressStore`、`ConfirmedMessagePublisher`、`DeadLetterService` 和 `BrokerManagementQueueClient`。

应用服务通过 `RuntimeWorkQueue`、`TaskProgressStore`、`MessagePublisher` 等接口使用能力。实际 Spring 驱动、AMQP 消息、Lua 指令留在适配层；没有声称更换任意中间件无需实现新适配器。旧持久化 key、JSON 字段、HTTP 路径、消息路由和数据库契约保持兼容。

## Native 与 Actions

根 `.github/workflows/native-build.yml` 对 `main`、`upgrade/**` 推送执行检查，也支持手动选择 Java 模块。所有编译通过 GitHub Actions，按用户要求停止本地 Java、Native、前端和 Python 构建。

- Java 全量回归使用真实 Valkey。Python 测试生成微型 BERT 并执行真实 CPU 推理和 HTTP 请求，测试不下载远程模型；两套前端分别执行 `npm ci`、lint、build 并保存产物。
- 从 `backend/settings.gradle` 推导 22 个 Java 部署模块，在对应 amd64/arm64 runner 构建 Native。搜索服务使用 10 Gi 编译堆、并行度 2，其余为 8 Gi、并行度 4，避免搜索模块在 ARM64 最终编译阶段耗尽堆。镜像保留全部 Native 本地库及证书/字体依赖，运行时使用明确堆上限并预留 RSS。
- Native migrator 在临时 PostgreSQL 中执行真实 Liquibase；内容安全服务验证 HTTP、JSON 和敏感词字典。额外的双架构检查在 PostgreSQL、Valkey、RabbitMQ 和带生产分词插件的空 Elasticsearch 上逐一启动全部 21 个 Java 服务，验证就绪状态和连接池预算；采集、内容和互动另验证运行期开关、原始视频入库、播放列表消费、重复消息和归一化交接去重。失败仍收集其余服务结果，但整体检查失败并阻止发布。
- AOT 子进程隔离 BuildKit 注入的 `OTEL_*`，固定 HTTP OTLP transport；所有 Java 服务明确运行期 HTTP transport，防止构建时生成 GRPC exporter 而运行期要求 HTTP。
- 采集、内容和互动消费者始终参与 AOT，使用监听容器的运行期 `autoStartup`。快照刷盘、watchdog、媒体请求和搜索对账保留 Bean，通过运行期布尔值控制定时入口，避免条件在构建时被固定。
- 镜像发布到既有 `docker.io/speedproxy`，新候选架构标签为 `YYYYMMDD-v<x.y.z>-production-test.1-<sha12>-amd64/arm64`，全部检查通过后生成 25 个同版本双架构标签；不覆盖已存在的制品，SBOM 与运行时版本统一。初始部署所用历史 sha 标签不改写。
- 仅主分支全部检查通过后，使用专用 GitOps deploy key 更新私有仓库 `ircs-prod/core/kustomization.yaml` 的 25 个映射。旧主分支构建发现有更新的 main 提交时跳过部署。
- Argo CD 的 core/edge Application 继续监听原私有 GitOps main。基础设施、迁移 Sync hook、分类器、业务服务与前端按波次执行；不使用会跳过 hook 的 selective sync。
- 手动 Docker Hub 工作流保留 JVM fallback，标签与 Native 分离。切换为 JVM 时必须同时调整容器参数，不能直接把 Native 的 `-Xmx` 可执行参数当作 JAR 应用参数。

## 生产配置和数据保留

三节点均可调度。全部 25 个应用 Deployment 设置全局软拓扑分散和同服务优先反亲和；网关 3 副本，两套前端各 2 副本，其余服务按单副本部署，共 29 个应用 Pod。保留数据卷可用性，不为均衡计数强制搬迁所有有状态数据。

主连接池容量合计最多 66，migrator 2，数据库 `max_connections=100`；预留审计短连接、运维及滚动更新容量。并发和 prefetch 继续有界，不能因为虚拟线程便无限增加数据库访问。

连接池环境变量使用 `SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE`、`MINIMUMIDLE`、`CONNECTIONTIMEOUT`、`IDLETIMEOUT`。旧写法把 connection 属性拆成嵌套 Bean，在绑定阶段提前调用连接 getter，导致 Hikari 启动后配置被锁定；现已修正生产和开发示例。Native 验证同时接受 Hikari 与 JDBC 池容量指标，生产检查读取真实 `max`、`active`、`pending`。

- 沿用 PostgreSQL、RabbitMQ、Elasticsearch、Valkey 的四个现有 PVC；四个 PV 回收策略改为 Retain，Namespace/有状态资源/PVC 使用 `Prune=false,Delete=false`，StatefulSet 保留 claim。
- Valkey 从 2 Gi 在线扩容到 16 Gi。`appendonly.aof.269.incr.aof` 中仅移除命令帧之间的 86 个 NUL 填充，保留全部 155,742 个有效命令，通过完整 AOF manifest 校验后启动。真实 PONG、AOF 写入/重写状态均为 ok。
- Valkey 探针显式比较 PONG，不能把 LOADING 或错误文本当作成功。既有 StatefulSet 的不可变 claim template 保持原值，独立声明现有 PVC 为 16 Gi，避免非法修改或容量回退。
- PostgreSQL 和 Elasticsearch 内存上限各提升到 2 Gi，RabbitMQ 1 Gi；Valkey 保持 5 Gi 并增加 CPU 配额。数据库/消息/搜索磁盘余量充足，没有盲目扩容这些盘。
- 存储服务使用新的 16 Gi 可扩展持久卷，StorageClass 回收策略 Retain，替代临时 emptyDir。WaitForFirstConsumer 的新 claim 与使用它的 Deployment 同波部署。
- 保留实际生产 ConfigMap/Secret 和启用的业务功能，重连各 V3 服务地址。原数据库里唯一残留的任务执行器 `ircs-dev` 内部地址已对齐到生产，并仅失效对应配置缓存。
- 网关、身份和互动服务共享既有 JWT Secret 引用，修复签发成功而网关校验返回 401。集群不存在旧 OTLP collector，当前关闭追踪采样和 OTLP 指标推送，保留 Prometheus 抓取；接入实际收集器后再恢复推送。
- 最初 V3/V4 的 84 个迁移资源逐文件哈希相同。审计修复候选随后新增四个并发索引 changeset，既有迁移 checksum 保持不变。切换前真实数据库有 170 条 Liquibase 记录、45,243 条原始视频、16,272 条统一视频；后续消费造成的正常增长单独观测。

截至 2026-11-13，当前候选为 3.2.2：

- V4 Application 和两个旧 Deployment/Service 已移除；V3 25 个 Deployment、29 个应用 Pod 就绪。四个旧数据 PVC 与新的 storage PVC 均 Bound，旧卷保留 Retain。
- 生产仍使用初始 V3 Native 镜像组，聚合服务单独使用已验证的临时修复镜像。原始/统一视频精确计数 45,243 / 16,272；Rabbit 正常队列已排空，但历史死信及部分 Valkey 工作队列仍需在新 Native 稳定后恢复，不清空掩盖。
- 旧 Native 在小堆与大 Valkey payload 下暴露 JDK 25/Netty 共享 Arena 支持缺失，并进一步造成响应解析错位。新增 `-H:+SharedArenaSupport`，配套 384 MiB 堆下重复读取 2 MiB 记录及精确队列计数验证；旧线上镜像尚未具备修复。
- 3.1.0 Java/Python 回归通过，Native migrator 双架构因 TagDatabaseChange 反射缺口失败，已取消该候选后续构建。3.1.1 补反射 hints 并集成审计修复。3.2.1 的 1700 项 Java、前端/Python 和 44 个双架构 Native 构建通过，运行门禁发现网关上游连接失败漏映射为 502，拒绝晋级。该异常转换在 3.2.2 修复；不放宽检查或覆盖原候选，当前以最新 Actions 结果为准。
- 管理端真实 PoW 登录、受保护 dashboard/tasks/raw/DLQ API，以及门户页面/资源和 Python CPU 推理已验证；它们不代表新候选已部署。完整审计复核、回归范围及兼容影响见 `../reports/137-v3-audit-remediation-and-native-release.md`。

## 兼容性、剩余边界与回退

本次保留 API、消息格式、队列名称、缓存 key 和 SQL schema，新增队列字段可由旧代码忽略。强制版本隔离已经停止 V4 消费者；旧版本不具备新的 owner/attempt/submission fencing，不应与新版本长期混跑。

Native 代码、反射/资源 hints 和 Linux 双架构实测共同构成验收，Windows 上的旧 DNS JNI 问题不作为 Linux 结果。前端 ESLint/TypeScript 使用最新 peer 兼容版；lint warning 仍是明确技术债务。没有事故日志，不能推断所有历史死信都是本次代码缺陷；死信必须按错误类型和幂等性检查后定向重放，禁止清空掩盖积压。

正常回退使用 GitOps 中上一组已验证的固定 V3 镜像映射。V3 首次切换失败时可先将应用缩到 0 保留数据，再修复候选；按用户授权不制作或依赖旧拆分仓库的 Git 备份。手动 JVM fallback 仍需独立构建、验证并调整运行参数。
